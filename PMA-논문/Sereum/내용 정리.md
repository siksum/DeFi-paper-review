# Sereum: Protecting Existing Smart Contracts Against Re-Entrancy Attacks

- 연도: 2019
- 저자: Michael Rodler, Wenting Li, Ghassan O. Karame, Lucas Davi
- 학회: Network and Distributed System Security Symposium (NDSS)
- DOI: `10.14722/ndss.2019.23413`
- 분석 근거: [원문 PDF](./Sereum.pdf), [원문 추출본](./Sereum.md)

## 논문 개요

Sereum은 이미 배포되어 코드를 고치기 어려운 Ethereum 스마트 컨트랙트를 재진입 공격으로부터 보호하기 위해 제안된 **실행 중 감시·차단 시스템**이다. 수정된 geth/EVM이 실제 트랜잭션을 실행하면서 opcode 수준의 데이터 흐름과 동적 호출 관계를 추적하고, 재진입한 실행이 아직 갱신되지 않은 storage 값을 의사결정에 사용한 뒤 이전 호출이 그 값을 뒤늦게 변경하려 하면 트랜잭션을 중단한다.

이 논문의 핵심은 `SLOAD`, `CALL`, `SSTORE`가 특정 순서로 나타나는지만 검사하는 것이 아니다. 실제 실행에서 다음 관계가 성립하는지를 추적한다.

```text
storage read(SLOAD)
  → 실제 산술·비교 연산을 통한 데이터 흐름
  → 조건 분기(JUMPI)의 조건값
  → 외부 호출 중 같은 컨트랙트 재진입
  → 이전 호출이 같은 storage 주소를 뒤늦게 갱신(SSTORE)
```

## 연구 질문

논문의 연구 질문은 다음과 같다.

> 이미 배포된 취약한 컨트랙트의 코드를 수정하지 않고, 그 컨트랙트의 업무 의미를 미리 알지 못해도 재진입 악용을 막을 수 있는가?

따라서 Sereum의 목적은 취약점을 배포 전에 찾는 정적 분석도, 공격 이후 공격자·피해자·손실을 설명하는 포렌식도 아니다. 실행 중인 트랜잭션에서 위험한 재진입 상태를 감지하고 실행을 되돌리는 것이 주목적이다.

## 주요 기여

- 기존 컨트랙트 코드를 수정하지 않는 EVM 수준의 runtime monitor를 설계했다.
- storage 값에서 조건 분기로 이어지는 실제 instruction-level dataflow를 동적 taint tracking으로 추적했다.
- 같은 컨트랙트가 여러 함수·여러 중간 컨트랙트를 거쳐 재진입하는 경우를 동적 호출 트리로 처리했다.
- 위험한 storage write를 감지하면 트랜잭션을 중단하고 상태 변화와 Ether 전송을 rollback한다.
- 기존 분석기가 놓칠 수 있는 cross-function, delegated, create-based 재진입을 제시하고 실험했다.
- 실제 Ethereum 과거 트랜잭션을 재실행해 탐지 결과, 오탐 원인, 성능 부담을 평가했다.

## 재진입과 공격의 구별

재진입 자체는 악성이 아니다. 외부 컨트랙트를 호출한 사이 그 외부 컨트랙트가 원래 컨트랙트를 다시 호출하는 구조는 정상 프로그램에도 존재할 수 있다.

Sereum이 위험하다고 보는 구조는 다음 세 조건의 결합이다.

1. 컨트랙트가 외부 호출을 수행한다.
2. 외부 호출이 진행되는 동안 같은 컨트랙트가 재진입되고, 재진입 실행이 persistent storage 값을 읽어 제어 흐름을 결정한다.
3. 외부 호출이 끝난 뒤 이전 호출이 그 storage 값을 갱신하려 한다.

즉, 재진입 실행은 나중에 변경될 값을 아직 변경되지 않은 상태로 읽어 의사결정을 내렸다. 논문은 이것을 inconsistent state에 기초한 실행으로 해석한다.

## 논문이 제시한 세 가지 고급 재진입

### 1. Cross-function reentrancy

공격자가 동일한 함수를 다시 호출하는 대신 같은 컨트랙트의 다른 함수를 호출한다. 두 함수가 같은 storage 상태를 읽거나 쓰면, 함수 이름이 달라도 불완전하게 갱신된 상태를 악용할 수 있다.

```text
Victim.withdraw()
  → Attacker callback
      → Victim.transferToken()  # 다른 함수로 재진입
  → Victim storage update
```

같은 함수의 재호출만 찾는 방어는 이 구조를 놓칠 수 있다.

### 2. Delegated reentrancy

외부 호출과 뒤늦은 상태 갱신이 컨트랙트와 동적 library에 나뉘어 나타난다. `DELEGATECALL` 또는 `CALLCODE`로 실행되는 library는 호출자와 storage context를 공유하므로, 개별 컨트랙트만 따로 분석하면 결합된 실행의 취약성이 보이지 않을 수 있다.

### 3. Create-based reentrancy

피해 컨트랙트가 `CREATE`로 새 컨트랙트를 만들고, 생성자의 실행이 공격자 컨트랙트를 거쳐 피해 컨트랙트를 다시 호출한다. 기존 분석기가 `CREATE`를 위험한 외부 호출로 취급하지 않으면 놓칠 수 있다.

## Sereum의 구조

![Sereum 구조](./images/6004ce3758e3d554f5b3504765a9442004c146f772b95f76030f765e21b7acb1.jpg)

Sereum은 geth의 EVM에 두 구성요소를 추가한다.

- **Taint engine**: storage에서 읽은 값이 실제 연산을 거쳐 어디에 사용되는지 추적한다.
- **Attack detector**: 동적 호출 트리와 taint 결과를 결합해 storage write-lock을 만들고 위반 시 트랜잭션을 중단한다.

### 1. Taint source: `SLOAD`

`SLOAD`가 storage 주소 `A`의 값을 읽으면, 값에 `DependsOnStorage(A)` 표식을 붙인다. 이 표식은 원래 데이터와 분리된 shadow stack·shadow memory·shadow storage에 저장된다.

### 2. 연산을 따라 taint 전파

산술·논리·비교 명령은 입력값의 taint를 출력값에 합쳐 전달한다. stack의 값을 memory로 복사하면 taint도 대응하는 shadow memory로 복사한다.

예를 들어 다음 실행에서 `LT` 결과는 storage 주소 `A`에 의존한다.

```text
SLOAD(A) → V
PUSH C
LT(V, C) → b
JUMPI(dst, b)
```

따라서 단순히 `SLOAD`와 `JUMPI`가 같은 함수에 있다는 사실이 아니라, `SLOAD`의 실제 결과값이 `LT`를 거쳐 `JUMPI`의 조건값 `b`를 만들었다는 관계를 찾는다.

### 3. Taint sink: `JUMPI`

`JUMPI`가 실행될 때 조건값에 `DependsOnStorage(A)`가 남아 있으면, storage 주소 `A`가 해당 호출의 제어 흐름에 영향을 준 것으로 기록한다. 호출 노드 `i`에서 이렇게 기록된 주소 집합을 논문은 `D_i`로 표현한다.

### 4. 동적 호출 트리

![동적 호출 트리](./images/a54aa4af484bcb84ced956ed8e3c7ab59efaeeab3981100e253ce0dcb9d3c2aa.jpg)

트랜잭션에서 실제로 일어난 contract invocation마다 노드를 만든다. 자식 순서는 실행 순서, 깊이는 EVM call-stack 깊이에 대응한다. 같은 컨트랙트가 여러 함수와 중간 컨트랙트를 거쳐 반복 호출되어도, 주소와 실제 호출 관계를 기준으로 재진입 경로를 찾을 수 있다.

### 5. Write-lock과 `SSTORE`

현재 호출 노드 `i`의 하위 트리에서 같은 컨트랙트를 실행한 노드들의 `D_j`를 모아 잠금 집합 `L_i`를 만든다. 이전 호출이 `SSTORE`를 실행하려 할 때 대상 storage 주소가 잠겨 있으면 Sereum은 재진입 위반을 보고하고 트랜잭션을 중단한다. EVM은 해당 트랜잭션의 상태 변화와 Ether 전송을 되돌린다.

## 이 연구가 opcode를 보는 방식

결론부터 말하면 **opcode를 실제로 본다**. 다만 opcode의 존재나 고정된 순서를 패턴 매칭하는 연구는 아니다.

| 확인 대상 | Sereum의 처리 |
|---|---|
| `SLOAD` | storage-dependent taint를 생성 |
| 산술·논리·비교 opcode | stack/memory를 통해 taint를 전파 |
| `JUMPI` | storage 값이 의사결정에 도달했는지 확인 |
| `CALL`·`DELEGATECALL`·`CALLCODE`·`CREATE` | 실제 호출 트리와 재진입 관계 구성 |
| `SSTORE` | 잠긴 storage 주소의 뒤늦은 변경인지 확인 |

따라서 “state read → 연산 → 의사결정”의 instruction-level dataflow는 실행 trace와 각 opcode 전후의 stack·memory·storage taint를 함께 추적해 얻는다.

## 실행 시점: 포렌식인가?

| 구분 | Sereum |
|---|---|
| 주된 시점 | 트랜잭션 실행 중(runtime/inline) |
| 주된 출력 | 재진입 위반 경보 |
| 대응 | 즉시 abort와 rollback, 또는 passive warning |
| 평가 방법 | 과거 블록의 트랜잭션 재실행 |
| 사후 포렌식 결과 | 공격자 군집·피해자·수혜자·손실·경제적 서사는 제공하지 않음 |

과거 트랜잭션을 재실행해 이미 일어난 공격을 찾을 수 있으므로 사후 탐지에 응용할 수는 있다. 그러나 논문의 시스템 목적과 출력은 공격 사후의 전체 인과관계를 재구성하는 포렌식이 아니다.

## 평가

### 과거 트랜잭션 재실행

저자들은 Ethereum block 4,500,000까지의 트랜잭션을 재실행했다. 실행 시간이 매우 큰 DoS 대상 block은 제외했다.

| 항목 | 결과 |
|---|---:|
| 재실행 트랜잭션 | 77,987,922 |
| 생성된 컨트랙트 | 93,942 |
| 위반으로 경보한 트랜잭션 | 49,080 |
| 전체 재실행 트랜잭션 대비 경보 비율 | 0.063% |
| 최초 관련 컨트랙트 | 52 |
| 동일·유사 코드를 묶은 뒤의 그룹 | 16 |
| source code를 확인할 수 있었던 그룹 | 6/16 |

확인된 실제 재진입 실행은 다음 두 사례다.

- The DAO: 2,294개 공격 트랜잭션
- DSEthToken: 43개 트랜잭션. 악성 공격자가 아니라 취약점을 발견한 개발자들이 자금을 보호하기 위해 실행한 drain이었다.

논문은 전체 재실행 트랜잭션을 분모로 약 0.06%의 false-positive rate라고 표현한다. 하지만 이것은 **경보 precision과 같은 지표가 아니다**. source가 없는 일부 컨트랙트는 의미를 완전히 복원할 수 없었으므로, 49,080개 경보 중 최종적으로 몇 개가 참이었는지를 확정하는 precision은 논문만으로 계산할 수 없다.

### 세 고급 공격 테스트

cross-function, delegated, create-based 재진입 각각에 대해 공격 트랜잭션을 만들었고, Sereum은 세 공격을 모두 탐지했다. 이는 세 테스트에서의 기능 검증이며 모든 변형에 대한 일반적 recall을 뜻하지는 않는다.

### 성능과 메모리

| 항목 | 일반 geth | Sereum | 차이 |
|---|---:|---:|---:|
| 50개 block batch 평균 실행시간 | 2,277.0 ms | 2,494.5 ms | +217.6 ms, 9.6% |
| 평균 메모리 사용량 | 9,252 MB | 9,767 MB | +515 MB |

실험은 50개 block을 10,000회 반복한 결과다. 경보로 조기 중단된 트랜잭션은 성능 비교에서 제외했다. 저자들은 이를 negligible overhead로 해석하지만, 특정 시기의 geth와 제한된 block 표본에서 나온 결과이므로 현재 EVM 체인 전체에 그대로 일반화할 수는 없다.

## 한계점

### 1. Storage에서 control-flow로 가는 흐름에 집중

기본 설계는 `SLOAD → ... → JUMPI`를 찾는다. storage 값이 분기에는 사용되지 않고 곧바로 Ether 전송액이나 외부 호출 인자로 사용되는 재진입은 직접 포착하지 않는다. 논문도 외부 호출의 Ether amount나 calldata에 전달되는 변수까지 잠그도록 확장할 수 있다고 설명하지만, 기본 구현의 평가 대상은 아니다.

### 2. 실행된 경로만 관측

동적 분석이므로 실제로 실행된 경로는 정밀하게 보지만, 아직 실행되지 않은 잠재 취약 경로는 찾지 않는다. 공격 트랜잭션이 실행되어야 탐지할 수 있다.

### 3. EVM word 수준의 의미 손실

서로 다른 Solidity struct field가 하나의 32-byte storage slot에 들어가면 bytecode 수준에서는 구별하기 어렵다. 한 field의 taint가 다른 field까지 오염시키는 over-tainting으로 오탐이 발생할 수 있다.

### 4. `delete`와 0 대입을 구별하지 못함

EVM에서는 storage 해제도 0을 쓰는 `SSTORE`로 나타나므로, `delete M[id]`와 `M[id] = 0`의 고수준 의미를 bytecode만으로 구별할 수 없다.

### 5. 정상 재진입과 신뢰 관계의 의미 부족

다음 정상 또는 방어적 구조가 공격 패턴과 유사해 오탐을 만들 수 있다.

- 자식 컨트랙트 생성자가 부모로 callback하는 구조
- 서로 신뢰하는 컨트랙트들이 복잡하게 상호 호출하는 구조
- 컨트랙트가 자체 mutex로 재진입을 막는 구조

Sereum은 source나 trust relation을 모르기 때문에 이 의미를 직접 구분하지 못한다.

### 6. 수정된 EVM 필요

컨트랙트 코드는 고치지 않아도 되지만 geth/EVM 실행기를 수정해야 한다. 실제 네트워크에서 모든 위험 트랜잭션을 일관되게 차단하려면 client와 consensus 환경에 통합되어야 한다.

### 7. 공격자·피해자·손익을 복원하지 않음

경보는 위험한 재진입 실행과 storage 주소를 말할 수 있지만 다음을 계산하지 않는다.

- 어떤 주소들이 하나의 공격 주체인지
- 최종 수혜자가 누구인지
- 어느 주체가 손실을 부담했는지
- 공격자의 실제 순이익과 반사실 추가이익
- 피해자의 반사실 손실

## PMA 연구에 주는 시사점

### 직접 가져올 수 있는 원리

Sereum은 PMA를 탐지하지 않지만, **값을 읽었다는 사실과 그 값을 실제 의사결정에 소비했다는 사실을 구별하는 방법**을 보여준다.

예를 들어 어떤 lending 컨트랙트가 DEX pool을 호출했다는 사실만으로는 그 가격을 대출액 계산에 사용했다고 증명할 수 없다. Sereum의 원리를 확장한다면 다음과 같은 증거 경로를 후보로 생각할 수 있다.

```text
DEX/oracle CALL·STATICCALL의 반환값
  → RETURNDATACOPY·memory·stack
  → 산술·비교 연산
  → JUMPI 또는 대출액·인출액 계산
  → settlement CALL/SSTORE
```

### 그대로 가져오면 안 되는 부분

- `SLOAD`만 source로 삼으면 외부 oracle 반환값을 놓친다.
- `JUMPI`만 sink로 삼으면 분기 없이 정산 금액에 직접 사용된 값을 놓친다.
- taint가 도달했다는 사실은 값의 경제적 의미, 가격 왜곡 여부, 정상 reference, 반사실 이익을 증명하지 않는다.
- opcode dataflow만으로 `Trade`, `Borrow`, `Deposit` 같은 semantic action이 자동 결정되지는 않는다.

### 현재 연구상 판정

- 상태: **`PROPOSED` — PMA 핵심 선행연구가 아니라 causal-evidence 구성요소를 제공하는 인접 연구**
- 유용한 부분: instruction-level data dependency, dynamic call tree, 실제 소비 지점 증거
- 부족한 부분: 경제값·왜곡·reference·semantic action·정산 의미·공격자/피해자 귀속·이익/손실
- 아직 확정하면 안 되는 주장: “Sereum의 taint 방식을 확장하면 PMA 전체 인과 그래프를 만들 수 있다.” 이는 별도 사례 실험과 반례 검증이 필요한 방법론 후보일 뿐이다.

## 한 줄 평가

Sereum은 실제 EVM 실행에서 `상태 읽기 → 연산 → 제어 의사결정 → 재진입 후 뒤늦은 상태 갱신`을 연결하는 강한 실행 증거를 제공하지만, 경제적 공격 서사와 손익 귀속을 만드는 포렌식 시스템은 아니다.
