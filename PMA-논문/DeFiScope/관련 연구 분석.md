## 이 논문을 이해하기 위한 전체 그림

### 우선 알아야 할 핵심

DeFiScope는 **가격을 정확히 계산해 정상가와 비교하는 도구가 아니다.** 다음 두 가지를 각각 복원한 뒤 합친다.

```text
A. 이 transaction에서 무슨 행위가 일어났는가?
   Transfer 흐름 → Swap, Deposit, Borrow, Withdraw 등

B. 이 transaction으로 특정 pool·protocol의 가격이
   올라가는 방향인가, 내려가는 방향인가?
   가격 관련 코드 + token balance change → LLM의 방향 추론

A의 행위 순서 + B의 가격 방향
→ 8개 공격 pattern과 맞는지 검사
→ 맞으면 PMA 후보
```

### 아주 단순한 예시

어떤 pool의 가격 코드가 다음과 같다고 하자.

```solidity
priceOfX = balanceOfYInPool / balanceOfXInPool;
```

transaction의 Transfer를 합산했더니:

```text
Pool의 Token X 잔액: +100
Pool의 Token Y 잔액: -50
```

였다. 그럼 정확한 실행 전후 가격을 몰라도 다음은 알 수 있다.

```text
분자 Y는 작아짐
분모 X는 커짐
→ X의 Y 표시 가격은 내려감
```

DeFiScope는 이 종류의 **가격 방향 추론**을 LLM에게 시킨다. 그러나:

```text
실행 전 가격 = 2,000
실행 후 가격 = 500
왜곡률 = -75%
```

처럼 정확한 값을 계산하는 것은 아니다.

### 두 파이프라인이 합쳐지는 지점

```text
Transfer Graph에서 복원:
Swap → Deposit → Borrow

LLM이 추론:
담보 token 가격 상승 또는 borrow token 가격 하락

둘을 결합:
가격을 유리하게 바꾼 뒤 과도하게 Borrow하는 pattern과 일치
```

따라서 DeFiScope는 정확히는 **“가격 변화 방향과 DeFi 행위 순서가 알려진 공격 구조와 닮았는지”**를 보는 탐지기다.

### 이 문서에서 구분할 다섯 가지

| 개념 | 뜻 | DeFiScope의 처리 |
|---|---|---|
| Swap 체결비율 | 특정 거래의 `amountOut/amountIn` | 핵심 가격 출력으로 직접 계산하지 않음 |
| Pool local price | 특정 pool 상태의 spot/quote price | 정확한 값 대신 방향만 추론 |
| Custom valuation | median·EMA·share ratio 등 protocol 내부 평가값 | open-source면 코드를 LLM이 해석 |
| Consumed value | Borrow·Withdraw 계산이 실제로 읽은 값 | value-level로 추적하지 않음 |
| Distortion | reference/counterfactual 대비 왜곡된 값 | 정확한 reference·왜곡량을 계산하지 않음 |

# 2. 논문이 푸는 문제

## 저자의 문제 정의

기존 PMA detector는 주로 다음 중 하나를 사용했다.

```text
당시 token exchange rate를 계산해 순차 비교
또는
과거 가격으로 정상 범위를 만들어 비교
```

저자들은 이 방법이 커스텀 가격 모델에 약하다고 본다. 예를 들어 UwULend는 sUSDe 가격을 하나의 Swap 비율로 정하지 않고, 여러 pool의 순간가격과 EMA를 모아 median으로 정했다.

저자들의 해법은 다음과 같다.

```text
복잡한 정확 가격을 굳이 계산하지 말고,
가격 코드와 token balance change를 LLM에게 주어
가격이 상승·하락하는 방향만 추론한다.

그런 뒤 그 방향이
Swap·Deposit·Borrow·Withdraw 등의 공격 순서와 맞는지 본다.
```

## 실제 처리 순서

### 2.1 Raw transaction 분할

하나의 외부 transaction에는 여러 contract call과 여러 DeFi 행위가 섞여 있다. DeFiScope는 사용자가 통제하는 account와 protocol contract 사이의 internal transaction을 `user invocation`이라고 부르고, 이 단위로 transfer와 함수 호출을 묶는다.

### 2.2 Transfer Graph 구성

각 transfer를 다음 edge로 만든다.

```text
보낸 주소 ──[token, amount, order]──> 받은 주소
```

예를 들어 router·relayer 여러 개를 거쳤더라도, 사용자가 Token X를 보내고 Token Y를 돌려받았다면 경로를 연결해 Swap으로 복원한다.

### 2.3 Semantic operation 복원

논문은 다음 6개 operation을 정의한다.

| Operation | 쉽게 설명 | 주요 토큰 흐름 |
|---|---|---|
| Swap | 한 token을 내고 다른 token을 받음 | user → pool → user, 시작·종료 token 다름 |
| Deposit | 자산을 예치하고 proof/share token을 받음 | deposit token 전송 + proof token mint |
| Withdraw | proof/share token을 소각하고 자산을 돌려받음 | proof token burn + asset 수령 |
| Borrow | 자산을 빌리고 debt token이 생김 | borrowed token 수령 + debt token mint |
| Stake | proof token 없이 자산을 맡김 | user → staking contract |
| Claim | 소각 없이 예치물·보상을 받음 | staking/claim contract → user |

### 2.4 주소·token별 balance change 계산

각 user invocation에서 주소·token별로 모든 Transfer를 합산한다.

\[
\Delta balance(a,t)
=
\text{token inflow}(a,t)-\text{token outflow}(a,t)
\]

예:

```text
Pool A로 USDC 1,000 유입
Pool A에서 USDC 200 유출
→ Pool A의 USDC balance change = +800
```

이 계산은 LLM이 하는 것이 아니라 전처리가 한다. mint·burn은 zero/dead address와의 Transfer를 사용해 total supply change로 바꾼다.

### 2.5 가격 관련 코드 후보 추출

오픈소스 contract이면:

```text
transaction trace에서 호출된 contract·function 확인
→ explorer API에서 verified source 다운로드
→ dependency를 펼쳐 컴파일
→ 함수명 keyword로 가격 관련 후보 선택
→ Slither call graph로 후보 함수와 호출된 하위 함수를 잘라 code snippet 생성
```

공개 코드의 keyword에는 `price`, `getAmount`, `latestAnswer`, `swap...`, `reward`, `valueOf`, `buy`, `sell`, `borrowSC` 등이 있다. 즉 가격 함수를 정확히 알고 자르는 것이 아니라 **가격과 관련됐을 것으로 보이는 코드 후보를 자른다.**

### 2.6 LLM에 넣는 것

LLM은 전체 project나 raw transaction을 그대로 받지 않는다. 전처리된 다음 정보를 받는다.

```text
1. 가격 관련 Solidity code snippet
2. 관련 contract의 token balance change
3. mint/burn으로 추정한 total supply change
4. token 가격이 증가한다 / 감소한다는 두 반대 문장
```

LLM은 먼저 코드에서 가격 모델을 설명하고, 두 문장에 1~10점을 매긴다.

```text
“가격 증가” 점수가 더 높음 → INCREASE
“가격 감소” 점수가 더 높음 → DECREASE
두 점수가 같음 → UNCERTAIN
```

이는 코드를 EVM으로 실행해 정확한 전후 가격을 구하는 방식이 아니다. **코드 관계와 delta를 이용한 부호 추론**이다.

### 2.7 Open-source custom model과 closed-source pool의 차이

| 경우 | 소스 | 가격 모델 처리 | LLM 입력 |
|---|---|---|---|
| Open-source standard pool | 있음 | 실제 코드에서 해석 | code snippet + delta |
| Open-source custom model | 있음 | CPMM으로 가정하지 않고 실제 코드를 해석 | custom code snippet + delta |
| Closed-source 2-token pool | 없음 | CPMM이라고 가정 | CPMM 설명 + delta |
| Closed-source custom model | 없음 | 실제 모델을 알 수 없음 | 일반적으로 지원 불가 |

중요한 점은 **커스텀 모델 전체를 CPMM으로 가정하는 것이 아니라는 것**이다. CPMM 가정은 source가 없는 2-token liquidity pool fallback에만 적용된다.

### 2.8 Semantic operation과 8개 공격 pattern 대조

가격 방향만으로는 공격을 판단할 수 없다. 정상 Swap·arbitrage·large trade에서도 가격은 바뀌기 때문이다. 그래서 다음 4개 family와 각 family의 순서 변형을 포함한 8 pattern을 사용한다.

| Family | 쉽게 설명한 공격 흐름 | 유리한 가격 방향 |
|---|---|---|
| Buy & Sell | token을 획득한 뒤 가격을 바꿔 매도 | 매도 token 상승 또는 상대 token 하락 |
| Deposit & Borrow | 담보를 예치하고 평가가를 유리하게 바꿔 과도 차입 | 담보 상승 또는 borrow token 하락 |
| Stake & Claim | stake 후 보상 환산율을 유리하게 바꿔 과다 claim | stake token 상승 또는 reward token 하락 |
| Deposit & Withdraw | proof/share token의 환산율을 유리하게 바꿔 과다 인출 | proof token 상승 또는 withdraw token 하락 |

## UwULend 예시로 다시 보기

UwULend는 sUSDe 가격을 여러 pool의 순간 USDe 가격과 EMA의 median으로 계산했다.

```text
공격자가 여러 pool에서 USDe balance를 큰 폭으로 변화
→ 각 pool의 instant USDe price가 하락하는 방향
→ 가격 provider의 median sUSDe price도 하락하는 방향
→ lending에서 sUSDe를 더 많이 Borrow할 수 있는 구조
```

DeFiScope는:

1. 여러 pool의 Transfer에서 balance change를 계산한다.
2. sUSDe price provider의 median 관련 코드를 자른다.
3. LLM에게 코드와 balance change를 주어 sUSDe price 하락 방향을 추론하게 한다.
4. Deposit·Borrow operation과 가격 하락 방향이 Pattern IV와 맞는지 본다.

그러나 DeFiScope가 정확한 `4.2%` 하락을 직접 재계산하거나, Borrow 계산이 어떤 return value를 소비했는지를 opcode-level로 추적하는 것은 아니다.

## 우리 문제와의 관계

- 직접 해결하는 부분:
  - raw token transfer에서 6개 semantic operation을 복원
  - 주소·token별 balance/supply delta 복원
  - pool·token·price direction 후보
  - operation·price direction pattern을 이용한 PMA 후보 판정
- 부분적으로만 해결하는 부분:
  - 개입 행위와 후속 Borrow·Withdraw 사이의 연결
  - user-controlled account 후보
- 다루지 않는 부분:
  - 정확한 왜곡값·reference·counterfactual
  - 왜곡값의 실제 read·return·settlement data-flow
  - attacker·beneficiary·victim·loss bearer 귀속
  - actual P&L·반사실 추가이익·피해자 손실

# 3. Scope와 Threat Model

## 쉽게 설명

DeFiScope는 실행된 transaction을 보고 PMA인지 판단한다. 주로 하나의 atomic transaction 안에서 가격 변화와 이용 행위가 함께 완료되는 사례를 대상으로 한다.

| 질문 | 답 | 근거 | 상태 |
|---|---|---|---|
| 어떤 공격을 대상으로 하는가? | standard·custom price model을 조작해 이익을 취하는 실행된 DeFi PMA | Abstract, Sections I–II | `[V]` |
| PMA를 어떻게 형식화하는가? | 일반 필요·충분조건보다 4 family·8 operation+direction pattern으로 구현 | Section VI, Table I | `[I]` |
| 성공한 공격만 보는가? | historical executed attack과 suspicious transaction을 중심으로 평가 | Section VII | `[V]` |
| 취약점만 있고 실행되지 않은 경우도 찾는가? | 아님. transaction-level attack detection이 목적 | Abstract, Section III | `[V]` |
| 공격자가 할 수 있는 일 | Swap, Deposit, Borrow, Stake, Claim, Withdraw, mint/burn·balance manipulation | Sections II, V–VI | `[V]` |
| flash loan이 필수인가? | 형식적 필수조건으로 제시하지 않음 | attack patterns | `[NR]` |
| 여러 주소를 하나의 공격자로 군집하는가? | user-controlled accounts 집합은 사용하지만 ownership/control clustering 근거는 약함 | Section V, supplementary G | `[I]` |
| 시간 범위 | 하나의 raw transaction | Sections V, VIII | `[V]` |
| multi-transaction attack | 미지원 | Section VIII | `[V]` |
| 기본 chain | Ethereum, BSC | Section VII | `[V]` |
| 추가 사례 | Polygon, Arbitrum 7건을 supplementary에 보고 | Section VIII, supplementary H | `[V]` |

## 범위 반례

- 정상 대형 Swap도 큰 price direction change를 만들 수 있다.
- 정상 arbitrage도 Buy→Sell과 이익을 포함한다.
- 정상 liquidation도 Borrow·asset transfer와 유사한 흐름을 만들 수 있다.
- `[V]` 같은 EOA가 통제하는 contract끼리의 정상 흐름을 closed-source DEX로 잘못 본 5개 false positive가 있다. 근거: supplementary G.
- `[V]` cross-transaction, non-ERC20, missing source, compile failure, closed-source custom model은 false negative를 만든다. 근거: Sections VII-A, VIII.

# 4. Observation Model: 무엇을 실제로 보는가

## 쉽게 설명

DeFiScope가 transaction에서 실제로 읽는 핵심 증거는 다음 세 종류다.

```text
1. 누가 어떤 contract function을 호출했는지
2. 어떤 token이 누구에게 얼마나 Transfer됐는지
3. 호출된 contract의 verified source code가 무엇인지
```

반면 다음은 완전히 복원하지 않는다.

```text
가격 함수가 읽은 모든 storage 값
호출 시점의 stack·memory
실제 price return value가 Borrow 계산으로 전달된 data-flow
조작이 없었을 counterfactual state
```

| 증거 | 입력 | 어디에 사용하는가 | 필수/선택 | 얻는 방법 | 없으면 어떻게 되는가 | 근거 |

## 가격 함수 후보를 어떻게 자르는가

공개 구현의 실제 순서는 다음과 같다.

```text
호출된 function 이름에 price/getAmount/latestAnswer/swap/... keyword가 있는가?
→ 있으면 후보 entry function
→ Slither로 그 함수가 호출하는 internal/high-level function을 전개
→ entry function + callees의 source snippet 추출
→ LLM에 전달
```

따라서 “가격 함수를 정확히 찾았다”가 아니라 “가격 관련으로 보이는 함수 묶음을 만들었다”가 정확하다.

## 입력과 정답의 분리

- 방법 입력:
  - transaction/call/log
  - verified source·ABI·dependency
  - function keyword list
  - 6-operation ontology
  - fine-tuned LLM
  - 8 attack patterns
- 평가에만 사용:
  - known PMA transaction
  - incident report
  - explorer hacker tag
  - D2 신규 사례의 manual abnormality·profit check
- preferred source → fallback → 실패:

```text
verified source + Type-I
→ source 없는 2-token pool이면 CPMM Type-II
→ closed-source custom model·compile failure면 미탐/부정확
```

# 6. Semantic Model과 그래프

## 쉽게 설명

Transfer Graph는 **돈의 이동 그래프**이지, 모든 인과관계를 담은 그래프가 아니다.

```text
보존:
누가 누구에게 무슨 token을 얼마나, 언제 보냈는가

어떤 storage 값이 어떤 함수 return을 만들고
```

## Semantic operation 평가

Ethereum transaction 1,000건에서 사람이 204개 operation을 식별한 후 TG와 reproduced CFT를 비교했다.

| 방법 | TP | FP | FN | Precision | Recall(TPR) |

- TG가 복원했다고 한 operation은 대부분 맞았다.

- 그러나 18개 operation을 놓쳤고, 새 ontology·non-standard action으로의 일반화는 별도 문제다.

# 7. Distortion, Profit, Loss 계산

## 먼저 쉽게 설명

DeFiScope는 이 부분을 거의 계산하지 않는다.

```text
알려고 하는 것:
특정 pool·protocol에서 특정 token 가격이 올라가는지/내려가는지

알려고 하지 않는 것:
정상가가 얼마인지
가격이 정확히 몇 % 왜곡됐는지
공격자가 조작 덕분에 얼마를 더 벌었는지
피해자가 조작 때문에 얼마를 잃었는지
```

논문이 사용하는 방향 추론을 우리가 수식으로 재구성하면:

\[
\operatorname{sign}\left(f(S+\Delta S)-f(S)\right)
\]

이다. 다만 논문은 실제 `S`와 `f(S)`를 전부 실행해 계산하지 않고 LLM score로 구현한다.

## 변화량만으로 방향을 알 수 없는 반례

\[
P=\frac{A}{S},\qquad \Delta A=10,\quad\Delta S=100
\]

이면:

\[
P'>P \iff 10S>100A
\]

이므로 실행 전 `A`, `S`를 모르면 방향도 알 수 없다. median·threshold·TWAP·EMA·oracle·rounding이 있는 커스텀 모델도 마찬가지다. 이런 경우 LLM의 단일 방향 출력은 실행 기반 증명이 아니다.

## 계산 커버리지

| 계산 대상 | DeFiScope의 정의·수식 | 기준 시점 | 단위 | reference/counterfactual | 판정 |
|---|---|---|---|---|---|
| price direction | increase/decrease statement score | user invocation/transaction | 방향 | 없음 | `P` |
| exact distorted price | 없음 | - | - | 없음 | `0` |
| normal/reference price | 없음 | - | - | 없음 | `0` |
| balance delta | inflow-outflow | invocation | raw token amount | 불필요 | `D` |
| transaction P&L | 없음 | - | - | 없음 | `0` |
| actual net worth change | 없음 | - | - | 없음 | `0` |
| manipulation-attributable gain | 없음 | - | - | 없음 | `0` |
| victim loss | D1의 incident-reported loss를 evaluation metadata로만 사용 | incident | USD | 방법 내 계산 없음 | `M/0` |
| bad debt·사회화 손실 | 없음 | - | - | 없음 | `0` |

## Profit이 어디에 쓰였는가

D2에서 새로 발견했다고 주장한 사례를 수동 확인할 때는:

1. abnormal token price/exchange-rate change가 있는지
2. initiator가 그 변화로 profit을 얻었는지

를 봤다. 이는 **ground truth 구축 기준**이지, DeFiScope의 탐지 결과가 counterfactual profit을 계산해 출력한 것이 아니다.

# 8. 최종 판정과 정상 반례

## 판정 규칙

최종 판정을 쉽게 쓰면:

```text
복원된 DeFi operation이 있는가?
+
연관 pool·token의 가격 방향이 있는가?
+
둘의 순서·token·pool 조합이 8 pattern 중 하나와 맞는가?
=
PMA 후보
```

LLM이 출력한 increase/decrease 점수가 같으면 `UNCERTAIN`으로 두고, 공개 구현은 uncertainty만 남은 결과를 제거할 수 있다.

## 왜 가격 변화만으로 판정하지 않는가

정상적인 Swap도 price direction을 바꾼다. 그래서 semantic action은 다음 질문에 답하기 위해 사용된다.

> 이 가격 변화가 자산을 획득·예치한 뒤 매도·차입·인출·claim을 유리하게 만드는 순서로 사용됐는가?

그러나 pattern match는 악의를 증명하거나, 정확한 manipulated return value가 settlement에 쓰였다고 증명하는 것은 아니다.

## Hard negative

| 정상·경계 사례 | 데이터에 명시적으로 포함 | DeFiScope가 구별하려는 근거 | 별도 평가 | 남는 혼동 |
|---|:---:|---|---|---|
| 정상 arbitrage | 미확인 | 8 pattern 전체 일치 부재 기대 | 없음 | Buy&Sell과 유사 |
| 정상 liquidation | 미확인 | supported operation/pattern 차이 기대 | 없음 | Borrow·Claim 흐름과 혼동 가능 |
| large swap | 미확인 | 후속 exploit operation 부재 기대 | 없음 | 정상 price impact와 manipulation 미분리 |
| JIT liquidity | 미확인 | pattern 미일치 기대 | 없음 | Deposit·Withdraw과 유사 |
| donation/rebase | 미확인 | operation·pattern 차이 기대 | 없음 | balance/supply manipulation과 유사 |
| 가격 충격은 있지만 consumer 없음 | 미확인 | Borrow/Withdraw/Claim 등 후속 pattern 부재 | 없음 | pattern이 actual data-flow는 아님 |
| same-owner contract 간 정상 흐름 | D2에 있음 | ownership/control clustering 필요 | 5 FP | closed-source DEX로 오분류 |

## 예상 오탐·미탐

- 가장 명확한 오탐: 같은 소유자의 contract 끼리 일어난 정상 흐름을 공격자↔DEX 흐름으로 오인.
- 가장 명확한 미탐:
  - cross-transaction attack
  - non-ERC20·internal ledger action
  - source missing·compile failure
  - closed-source custom price model
  - 실행 전 state가 필요한 복잡한 quantitative model

## 평가가 보장하는 것

- D1 95건에서 DeFiScope가 76건을 탐지했다.
- D2 suspicious set에서 147/153 precision을 보였다.
- D3 random benign sample 96,800건에서 false alarm이 없었다.
- 해당 1,000-transaction benchmark에서 TG가 CFT보다 높은 operation recall을 보였다.

## 평가가 보장하지 않는 것

- PMA 전체 모집단의 recall
- unseen protocol·unseen attack family에서의 일반화
- 개별 LLM direction output의 수학적 타당성·calibration
- 정확한 distortion·consumption·P&L·victim loss
- hard-negative family별 discrimination
- 일반 transaction 모집단에서의 precision

# 10. 가정·한계·재현성 감사

## 먼저 쉽게 정리

DeFiScope의 핵심 한계는 다음 네 문장으로 요약할 수 있다.

1. 소스를 구하고 컴파일할 수 있어야 open-source custom model을 분석한다.
2. 모든 가격 입력이 아닌 balance/supply delta만으로 LLM이 방향을 추론한다.
3. 방향과 semantic pattern의 일치는 consumption·settlement의 value-level 증명이 아니다.
4. attacker·victim·profit·loss를 방법 출력으로 완전히 계산하지 않는다.

| 항목 | 저자가 명시한 내용 | 우리 분석 | 심각도 | 근거 |
|---|---|---|:---:|---|
| Source availability | closed source·compile failure 한계 인정 | Type-I custom model의 필수 관측 조건 | 높음 | Sections VII-A, VIII |

# 11. 우리 연구에 대한 판정

## 후보 gap별 판정

| Gap 후보 | 판정 | 논문이 보여준 근거 | 한정어 |
|---|---|---|---|
| protocol-specific 사전 지식 의존 | **부분 지원** | 수동 protocol formula는 없지만 keyword·ontology·pattern·source가 필요 | Type-I은 신규 source를 자동 수집 |
| 가격·평가 지점 자동 식별 부족 | **지원** | keyword+call graph는 candidate일 뿐 exact function/data dependency가 아님 | LLM이 candidate 내 model을 해석 |
| 개입→consumption→settlement 연결 부족 | **지원** | operation·direction pattern이지 value-level data-flow가 아님 | semantic consumer 후보는 제공 |
| attacker·victim 귀속 부족 | **지원** | UC 후보·incident label 외 독립 attribution schema 없음 | D2 hacker tag는 평가용 |
| actual P&L·조작 귀속 이익 부족 | **지원** | 방법론 내 exact/counterfactual 계산 없음 | D2 label에만 profit 사용 |
| 정상 유사 행위 구별 부족 | **부분 지원** | semantic pattern으로 price-only alert를 줄임; D2 6 FP | dedicated hard-negative 없음 |
| atomic transaction 제한 | **지원** | single transaction 제한으로 실제 FN 보고 | 저자는 multi-tx가 적다고 주장 |
| event/log 중심 관측 누락 | **부분 지원** | Transfer를 TG·delta의 핵심으로 사용 | call trace·source로 보완 |
| exact distortion/reference 부재 | **지원** | direction만 추론하고 정상가·왜곡량 미계산 | 의도적으로 exact rate를 피한 설계 |

## 이 논문에서 가져올 수 있는 것

- user-invocation-level time-indexed Transfer Graph
- raw evidence, semantic operation, price interpretation 계층의 분리
- semantic recovery 성능과 end-to-end detection 성능의 분리 평가
- source availability·compile failure·closed-source fallback을 분리한 오류 보고
- exact price를 구하지 않고도 direction+semantic pattern으로 탐지 후보를 줄이는 실용적 아이디어

## 그대로 가져오면 안 되는 것

- price direction을 exact distorted value로 저장
- pattern order를 actual consumption data-flow edge로 저장
- source/pre-state가 없는데도 LLM direction을 확정 증거로 사용
- closed-source 2-token contract를 무조건 CPMM으로 확정
- initiator를 attacker·beneficiary로 강제
- profit을 PMA의 충분한 증거로 사용

## 우리 설계에 대한 포함 제안

다음을 서로 다른 node·edge로 유지해야 한다.

```text
swap execution rate
≠ local pool spot/quote price
≠ custom price-model output
≠ protocol-consumed value
≠ settlement result
≠ actual asset/debt delta
≠ counterfactual gain/loss
```

source를 사용하더라도 core causal edge는 가능하면 runtime evidence로 검증해야 한다.

```text
preferred: trace·state·actual call return·data-flow
fallback: verified source·ABI·symbolic interpretation
실패: UNKNOWN + 누락이 판정에 미치는 영향
```

## 한 문장 결론

> DeFiScope는 token transfer에서 DeFi operation을 복원하고 source code·balance delta로 pool·token별 가격 방향을 추론한 뒤 8 pattern으로 PMA를 탐지하지만, exact distorted value·reference·value consumption·role attribution·counterfactual gain/loss를 복원하지 않으므로 우리의 causal-evidence gap을 **지원**한다.
