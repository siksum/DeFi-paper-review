> 논문: **Detecting Various DeFi Price Manipulations with LLM Reasoning**
>
> 저자: Juantao Zhong, Daoyuan Wu, Ye Liu, Maoyi Xie, Yang Liu, Yi Li, Ning Liu
>
> 발표: ASE 2025
>
> 검토일: 2026-08-11

> 근거: [원문 PDF](./DeFiScope.pdf), [원문 추출본](./DeFiScope.md), [공식 artifact](https://github.com/AIS2Lab/DeFiScope)

## 1. 한 문장으로 설명

DeFiScope는 정확한 전후 가격과 왜곡량을 계산하는 시스템이 아니라, **트랜잭션에서 관측한 토큰 잔액 변화와 가격 관련 소스코드를 LLM에 제공해 프로토콜 내부 가격의 증가·감소 방향을 추론하고, 그 방향이 Swap·Deposit·Borrow 등의 행위 순서와 사전 정의된 공격 패턴에 맞는지 검사하는 탐지기**다.

```text
원시 transaction
├─ Transfer Graph → Swap/Deposit/Borrow 등 semantic operation
└─ 주소·토큰별 잔액 변화 + 가격 관련 코드 → LLM 가격 방향

semantic operation 순서 + 풀·토큰별 가격 방향
→ 8개 공격 패턴과 대조
→ PMA 후보
```

## 2. 논문이 풀려는 문제

기존 방법은 토큰 교환비율을 추적하거나 과거 가격 범위와 비교하는데, 저자들은 이 방식이 복잡한 자금 흐름과 커스텀 가격 모델에서 잘 작동하지 않는다고 본다.

논문의 핵심 아이디어는 다음과 같다.

> 정확한 가격을 복원하지 않고도, 가격 계산 코드와 그 코드가 참조하는 것으로 가정한 토큰 잔액·총공급량의 변화를 보면 가격이 올라갈지 내려갈지 추론할 수 있다.

이 추론은 단독 공격 판정이 아니다. 복원한 DeFi operation과 결합해야 공격 후보가 된다.

## 3. 전체 파이프라인

### 3.1 Transaction을 user invocation으로 분할

논문은 사용자가 통제하는 EOA·contract와 다른 protocol contract 사이의 internal transaction을 `user invocation`으로 정의하고, 이를 최소 분석 단위로 사용한다.

하나의 외부 transaction에 여러 invocation이 있을 수 있으며, Transfer Graph와 잔액 변화는 기본적으로 이 구간에 맞춰 구성된다.

### 3.2 Transfer Graph 구성

Transfer Graph(TG)는 다음으로 구성된다.

- node: EOA, contract account, zero/dead address
- edge: `sender → receiver`의 token transfer
- edge attribute: token, amount, 발생 순서
- transfer type: transfer, mint, burn

핵심은 여러 relayer·router를 거친 토큰 흐름도 방향 그래프와 시간 순서로 연결하는 것이다.

### 3.3 Semantic operation 복원

논문은 상위 30개 DeFi app을 분석해 다음 6개 operation을 정의했다.

- `Swap`
- `Deposit`
- `Withdraw`
- `Borrow`
- `Stake`
- `Claim`

예를 들어 Swap은 user-controlled account에서 시작해 여러 contract를 거친 뒤 다른 token으로 user-controlled account에 돌아오는 경로를 찾는다. 경로의 시간 인덱스는 증가해야 하고, 첫 token과 마지막 token이 달라야 한다.

### 3.4 주소·토큰별 순잔액 변화 계산

Transfer를 주소·토큰별로 합산한다.

\[
\Delta balance(a,t)
=
\sum \text{inflow}(a,t)-\sum \text{outflow}(a,t)
\]

예:

```text
Pool A에 들어온 USDC: 1,000
Pool A에서 나간 USDC: 200
→ Pool A의 USDC 순변화: +800
```

Mint·burn은 zero/dead address와의 Transfer를 이용해 total supply 증가·감소로 표현한다.

### 3.5 가격 관련 소스코드 수집·추출

오픈소스 contract에는 Type-I inference를 적용한다.

1. transaction에서 호출된 contract 주소와 entry function을 알아낸다.
2. block explorer API로 verified source를 다운로드한다.
3. `slither-flat`으로 dependency를 하나의 Solidity 파일로 펼친다.
4. pragma에 맞는 solc 버전을 선택·설치하고 Slither로 컴파일한다.
5. 함수명 키워드로 가격 관련 entry-point 후보를 찾는다.
6. Slither call graph로 entry function의 internal·high-level callees를 전개해 코드 조각을 만든다.

공개 구현의 키워드에는 `price`, `getAmount`, `latestAnswer`, `swap...For...`, `reward`, `valueOf`, `get...Price`, `buy`, `sell`, `supply`, `borrowSC`, `cacheAssetPrice` 등이 있다.

즉 전체 project를 LLM에 넣는 것은 아니다.

```text
전체 dependency closure
→ 컴파일·호출 그래프 분석용

키워드 entry function + callees
→ LLM prompt용 code snippet
```

### 3.6 LLM의 가격 방향 추론

LLM은 다음을 받는다.

- 가격 계산 관련 Solidity code snippet
- 관련 contract·token의 balance 변화량
- mint·burn에 따른 total supply 변화량
- 토큰별 두 개의 반대 문장
  - “이 token의 가격이 증가한다”
  - “이 token의 가격이 감소한다”

LLM은 각 문장을 1~10점으로 평가한다.

```text
증가 점수 > 감소 점수 → INCREASE
증가 점수 < 감소 점수 → DECREASE
증가 점수 = 감소 점수 → UNCERTAIN
```

LLM의 역할은 두 단계다.

```text
Solidity code snippet
→ 고수준 가격 모델 해석

가격 모델 + balance/supply delta
→ 가격 출력의 방향 판단
```

### 3.7 공격 패턴 대조

가격 방향만으로는 공격이 아니다. DeFiScope는 다음 4개 family에 각각 두 개의 순서 변형을 두어 총 8개 pattern을 사용한다.

| family | 기본 구조 | 가격 방향의 역할 |
|---|---|---|
| Buy & Sell | token 획득 → 가격 변화 → 매도 | 매도 token 가격 상승 또는 상대 token 하락 |
| Deposit & Borrow | 담보 예치 → 가격 변화 → 차입 | 담보 가격 상승 또는 차입 token 가격 하락 |
| Stake & Claim | stake → 보상 token 가격 변화 → claim | 보상 token 가격 하락 등으로 과다 claim |
| Deposit & Withdraw | 예치·proof token → 가격 변화 → 인출 | proof/withdraw token 환산율을 유리하게 변화 |

각 family의 두 번째 pattern은 가격 변화가 첫 semantic operation보다 먼저 일어나는 변형을 허용한다.

## 4. 정확한 가격 계산과 방향 추론의 차이

DeFiScope는 실행 전후의 정확한 가격을 계산하는 방식이 아니다. 다음 부호만 추론한다.

\[
\operatorname{sign}
\left(
f(S+\Delta S)-f(S)
\right)
\]

### 4.1 실행 전 값 없이도 방향을 알 수 있는 경우

CPMM에서 token X의 Y 표시 가격이:

\[
P_X=\frac{y}{x}
\]

이고 Swap으로 `x 증가`, `y 감소`가 관측됐다면 양의 reserve에서 항상:

\[
\frac{y+\Delta y}{x+\Delta x}<\frac{y}{x}
\]

이다. 정확한 전후 reserve를 몰라도 가격이 내려가는 방향은 알 수 있다.

### 4.2 변화량만으로 방향을 알 수 없는 경우

\[
P=\frac{A}{S},\qquad \Delta A=10,\quad\Delta S=100
\]

이면:

\[
P'>P \iff 10S>100A
\]

이므로 실행 전 `A`, `S`를 모르면 가격 방향도 결정할 수 없다.

다음 모델도 실행 전 값·과거 상태·분기 조건이 필요할 수 있다.

- median의 순위에 의존하는 모델
- threshold로 식이 바뀌는 모델
- TWAP·EMA·누적값을 참조하는 모델
- oracle return value를 함께 사용하는 모델
- 잔액과 total supply가 함께 바뀌는 share-price 모델
- rounding·clamp·cache가 있는 모델

이런 경우 LLM이 하나의 방향을 선택해도 그 결과는 실행 기반 증명이 아니다.

## 5. 튜닝과 커스텀 가격 모델

### 5.1 protocol마다 튜닝하는 것은 아님

오프라인 fine-tuning은 Uniswap V2:BTC20 CPMM pool의 forked state에서 Foundry fuzzing으로 만든 샘플을 이용한다.

```text
학습 샘플:
가격 code + 토큰 balance-change pair + 상승/하락 정답
```

논문은 CPMM 상승 500개, 하락 500개의 database를 만들고, GPT fine-tuning에는 이 중 96개를 샘플링한다. 이렇게 튜닝한 하나의 모델을 여러 protocol에 적용한다.

### 5.2 오픈소스 커스텀 모델: Type-I

오픈소스 커스텀 모델을 CPMM으로 가정하는 것은 아니다. 해당 protocol의 실제 Solidity code snippet을 제공하고, LLM이 가격 모델을 해석한다.

```text
커스텀 Solidity code
+ balance/supply delta
→ LLM이 커스텀 가격 관계를 해석해 방향 판단
```

다만 모델이 CPMM 자료로만 튜닝됐다는 학습 분포와 적용 분포의 차이가 남는다. 논문은 커스텀 모델 공격에서 fine-tuned GPT-3.5의 탐지 성공률이 60%에서 93.3%로 올랐다고 보고하지만, 임의의 신규 모델에서의 정당성을 증명한 것은 아니다.

### 5.3 폐쇄소스 2-token pool: Type-II

소스가 없지만 Transfer Graph로 2-token liquidity pool로 판단한 경우, prompt에 그 pool이 CPMM을 사용한다고 명시한다.

```text
소스 없음
+ 2-token liquidity pool로 분류
+ CPMM 가정
+ token balance delta
→ LLM이 가격 방향 점수 출력
```

이 경우는 실제 price model을 복원한 것이 아니다. 풀이 CPMM이 아니면 전제가 틀리다. 또한 CPMM이 이미 확정됐다면 방향 판단은 결정적 규칙으로 수행할 수 있으므로 LLM의 필요성이 약하다.

### 5.4 폐쇄소스 커스텀 모델

2-token CPMM 가정으로 표현할 수 없는 폐쇄소스 커스텀 모델은 실질적으로 지원하지 못한다. 논문의 TIFIToken 미탐 원인 중 하나도 closed-source custom price model이다.

## 6. “왜곡”이라는 표현의 정확한 범위

DeFiScope가 직접 출력하는 것은 대략 다음이다.

```text
영향을 받은 것으로 추론된 pool/contract
+ token
+ INCREASE / DECREASE / UNCERTAIN
```

다음은 계산하지 않는다.

- 정확한 실행 전후 가격
- 정상 기준가격
- 기준가격 대비 왜곡량·왜곡률
- 조작이 없었을 반사실 가격
- 왜곡된 값이 실제로 읽힌 instruction·call·return
- 그 값이 Borrow·Withdraw의 정산식에 전달된 data-flow

따라서 문서에서는 다음을 구분한다.

```text
가격 방향 변화 = LLM이 추론한 관측 후보
왜곡 = 가격 방향이 semantic attack pattern과 일치할 때의 탐지 해석
```

정상 reference와 비교해 왜곡을 독립적으로 측정한 것은 아니다.

## 7. Semantic operation의 역할

가격이 올라가거나 내려가는 것은 정상 swap, arbitrage, liquidation, 대형 거래에서도 발생한다. 그래서 semantic operation을 복원해 다음을 본다.

> 이 가격 방향 변화가 어떤 경제적 행위 사이에 있으며, 후속 operation이 공격자에게 유리하게 이용하는 패턴인가?

예:

```text
Deposit collateral
→ collateral 가격 상승 또는 borrow token 가격 하락
→ Borrow
```

그러나 이것은 사전 정의된 구조적 pattern과의 일치지, 악의·반사실 이익·피해를 증명하는 것은 아니다.

## 8. Swap 비율로 커스텀 모델을 대체할 수 있는가

각 swap의 실제 체결비율은 유용한 상류 관측값이다.

\[
r_i=\frac{\text{Token Y amount out}}{\text{Token X amount in}}
\]

같은 pool의 순차 swap을 같은 quote 방향으로 정규화하면 트랜잭션 중 교환비율 변화를 볼 수 있다. 이는 DeFiRanger의 exchange-rate 추적과 유사한 접근이다.

다만 이 비율은:

- 특정 거래량에 대한 평균 체결가격이며 spot price와 다를 수 있다.
- 수수료·slippage·transfer-tax의 영향을 받는다.
- 거래 크기가 다르면 정상 price impact와 조작을 구분하기 어렵다.
- median·EMA·oracle·share ratio를 결합한 실제 커스텀 output과 같지 않다.
- swap이 없는 donation, mint/burn, vault share-price 조작을 못 본다.

그러므로 우리 연구에서는 다음 계층을 합치지 않는 것이 적합하다.

```text
swap execution rate
→ local pool spot/quote price
→ custom price-model output
→ protocol이 실제 소비한 value
→ settlement·asset/debt result
```

## 9. CoinGecko 같은 외부 API로 대체할 수 있는가

CoinGecko 등의 외부 시장가격은 다음 용도로는 유용하다.

- 공격 시점 유동 자산의 대략적인 시장가치
- P&L을 USD 등 공통 단위로 환산
- local pool price와 광범위한 market reference를 비교

하지만 다음을 대체하지 못한다.

- 트랜잭션 중간에만 존재한 일시적 pool price
- lending/vault가 실제로 읽은 oracle return
- LP/share/debt token의 protocol-internal valuation
- 가격을 조작하고 같은 transaction에서 복구한 순서
- 왜곡된 값이 settlement에 전달된 증거

따라서 외부 API는 reference의 하나이지, 프로토콜 내부 가격과 consumption 증거의 대체제가 아니다.

## 10. 소스코드 의존성과 실패 조건

소스 수집·컴파일은 실제 비용과 실패 가능성이 있다.

- unverified source
- proxy implementation·delegatecall 해결 실패
- dependency·library 누락
- compiler version·optimization setting 불일치
- Solidity/Vyper 정적 분석 실패
- 공격 시점의 구현과 수집한 소스의 불일치
- 동적 호출·외부 oracle dependency

D1의 95건 중 19건을 놓쳤고, 그중 8건은 source-code requirement를 만족하지 못했다.

```text
가격 함수 소스 없음: 3건
Slither 컴파일 실패: 5건
```

논문은 decompilation·수동 개입으로 완화할 수 있다고 쓰지만, 우리 연구의 관측 모델 관점에서는 **verified source가 없을 때 custom model을 분석하지 못하는 실제 관측 실패**다.

논문은 트랜잭션당 평균 2.5초를 보고한다.

```text
LLM price inference: 평균 1.40초
static analysis: 평균 0.97초
기타: 미미
```

다만 신규 contract의 cold-cache source download, compiler 설치, explorer 응답 시간이 어떻게 반영됐는지는 분리 보고되지 않았다.

## 11. 평가

### 11.1 D1: 알려진 PMA 95건

| 항목 | 결과 |
|---|---:|
| chain | Ethereum, BSC |
| protocol | 90개 DeFi application |
| 알려진 PMA | 95건 |
| 총 보고 손실 | $381.16M |
| DeFiScope 탐지 | 76/95, recall 80% |
| DeFort | 50/95, 52.6% |
| DeFiRanger | 49/95, 51.6% |
| DeFiTainter | 34/95, 35.8% |

19건의 미탐 원인은 다음을 포함한다.

- cross-transaction attack
- non-ERC20 token
- 복잡한 정량 추론에서 LLM 실패
- 가격 관련 source 부재
- Slither 컴파일 실패
- closed-source custom price model

비교 주의사항: DeFiRanger는 비공개라 일부는 기존 논문 결과를 사용하고, 나머지는 DeFiScope 저자들의 재구현으로 평가했다.

### 11.2 D2: suspicious transaction 968건

```text
경보: 153건
True Positive: 147건
False Positive: 6건
Precision: 96%
기존 미보고로 주장한 역사적 사고: 81건
```

새로운 사례의 수동 ground truth는:

1. 비정상적 token price 또는 exchange-rate 변화
2. 그 변화로 인한 initiator의 profit

을 함께 확인했다. 이 profit은 신규 사례의 수동 label 구축 기준이지, 탐지 pipeline이 계산한 반사실 추가이익이 아니다.

6건의 false positive 중:

- 5건: 같은 EOA가 생성·통제한 contract 간 정상 거래를 closed-source DEX로 오분류
- 1건: 실제 malicious logic attack이지만 PMA는 아님

주소 소유·통제 관계를 군집하지 못한 것이 실제 오탐으로 연결됐다.

### 11.3 D3: benign transaction 96,800건

DeFort의 428,523건 benign dataset에서 Ethereum·BSC transaction 96,800건을 무작위 샘플링했고, 이 세트에서 false alarm 0건을 보고했다.

그러나 정상 arbitrage, liquidation, large swap, JIT liquidity, donation 등을 보장한 전용 hard-negative 계층로 구성한 것은 아니다.

### 11.4 Semantic operation 복원 평가

Ethereum transaction 1,000건의 204개 수동 operation에 대해:

| 방법 | TP | FP | FN | Precision | TPR |
|---|---:|---:|---:|---:|---:|
| TG | 186 | 3 | 18 | 0.984 | 0.912 |
| reproduced CFT | - | - | - | 0.991 | 0.559 |

TG는 복잡한 relayer를 거친 swap 복원에서 CFT보다 높은 recall을 보였다.

## 12. 우리가 제기한 의문과 답

### Q1. Transfer에서 token 주소별로 기록하고 LLM에게 balance를 계산하라고 하는가?

아니다. balance delta 계산은 전처리가 수행한다. LLM은 잔액을 RPC로 조회하거나 Transfer를 합산하지 않고, 이미 만들어진 `증가·감소 by 수량`과 code snippet을 받는다.

### Q2. 비교할 값도 없는데 “가격이 변했다”는 것은 무엇인가?

시장 reference가가 아니라 트랜잭션 실행 전 상태 `S`와 delta 반영 후 `S+ΔS`의 함수 출력 방향을 뜻한다. 다만 실제 `S`가 prompt에 없는 경우가 있어, 단조성으로 부호가 결정되는 식이 아니면 방향도 증명되지 않는다.

### Q3. LLM이 소스코드를 실행해 정확한 가격을 계산하는가?

아니다. 탐지 단계에서 EVM을 replay해 `P_before`, `P_after`를 구하지 않는다. LLM은 code relationship과 delta에서 `INCREASE/DECREASE/UNCERTAIN`을 점수화한다. Foundry 실행은 오프라인 fine-tuning sample 생성에 사용된다.

### Q4. Swap calldata의 `amountIn`을 가격식에 대입하는가?

아니다. 주로 실제 ERC-20 Transfer를 합산한 protocol account의 token balance delta를 사용한다. `amountIn`, `amountOutMin`, `path`는 swap function의 calldata이고, 가격식의 state input인 reserve·balance·totalSupply와 같지 않다.

### Q5. protocol마다 LLM을 다시 튜닝해야 하는가?

아니다. LLM은 CPMM synthetic data로 한 번 fine-tuning한다. 다만 신규 transaction을 분석할 때마다 호출된 각 contract의 source를 가져와 candidate snippet을 새로 넣는다.

### Q6. 커스텀 가격 모델도 CPMM으로 가정하는가?

- open-source custom model: 아님. 실제 code snippet을 LLM이 해석한다.
- closed-source two-token pool: CPMM으로 가정한다.
- closed-source custom model: 일반적으로 지원하지 못한다.

### Q7. 가격 함수는 어떻게 찾는가?

함수명 keyword heuristic으로 entry function 후보를 찾고 Slither call graph로 callee를 확장한다. 실제 price function을 정확히 증명한 후 잘라내는 방식이 아니므로 누락·과잉 포함이 가능하다.

### Q8. CoinGecko 가격으로 대체할 수 있는가?

외부 market reference·USD 환산에는 유용하지만, 트랜잭션 중간에 잠깐 조작된 pool price와 protocol-consumed oracle/share value를 대체하지 못한다.

### Q9. 모든 Swap의 `amountOut/amountIn`을 비교하면 커스텀 모델도 볼 수 있는가?

특정 pool의 execution-rate 변화 관측에는 유용하다. 그러나 체결비율은 거래량·수수료·slippage에 의존하고, median·EMA·oracle·vault share 계산 결과와 같지 않다. 따라서 upstream observation으로는 쓸 수 있지만 custom output의 대체제는 아니다.

## 13. 인과 사슬 기준 커버리지

우리의 최소 인과 사슬에 대입하면:

```text
행위자 후보
→ 개입
→ 상태 변화
→ 왜곡된 경제값
→ 소비
→ 정산/의사결정
→ 자산·부채 결과
→ 수혜·손실
```

| 인과 요소 | DeFiScope 커버리지 |
|---|---|
| 행위자 후보 | user-controlled account 후보는 있지만 통제 군집·수혜자 귀속은 약함 |
| 개입 | Transfer·semantic operation으로 부분 복원 |
| 상태 변화 | token balance·total supply delta 복원 |
| 왜곡된 경제값 | pool·token별 방향 후보만 추론; 절대값·reference 없음 |
| 소비 | semantic pattern으로 연결하지만 actual value read/data-flow는 없음 |
| 정산·의사결정 | Borrow·Withdraw·Claim 등 operation 후보 |
| 자산·부채 결과 | token flow·mint/burn으로 부분 표현 |
| 수혜·손실 | 정형화된 beneficiary·victim·P&L·counterfactual 출력 없음 |

가장 긴 연결은 다음 정도다.

```text
관측된 transfer
→ semantic operation
→ token balance/supply delta
→ pool·token price-direction inference
→ operation/price pattern match
→ PMA 후보
```

다음은 연결하지 못한다.

```text
조작된 정확한 value
→ value read/return
→ settlement에서의 소비
→ 반사실 추가이익
→ 피해자·loss bearer의 손실
```

## 14. 핵심 장점과 한계

### 장점

- 교환비율만으로 표현하기 힘든 custom price model을 source-level reasoning 대상으로 삼았다.
- Transfer Graph로 relayer가 많은 복잡한 token flow를 operation으로 복원하려고 했다.
- 가격 변화만이 아니라 의미 행위 순서를 함께 사용한다.
- 원문·코드·데이터셋·보충자료가 공개되어 분석 가정을 검사할 수 있다.
- PMA benchmark, suspicious set, large benign set, semantic recovery 평가를 분리했다.

### 한계

- source availability·compilability가 Type-I의 중요 관측 전제다.
- 가격 함수 후보를 함수명 keyword와 정적 call graph로 찾는다.
- 공개 구현은 user call에서 transfer된 모든 token을 price calculation에 관련된 것으로 가정한다.
- 가격 모델의 모든 state input을 복원하지 않고 balance/supply delta를 사용한다.
- 정확한 가격·왜곡량·reference·counterfactual을 계산하지 않는다.
- 가격 output의 read·return·data dependency를 정산까지 추적하지 않는다.
- 폐쇄소스 2-token pool의 CPMM 가정은 틀릴 수 있다.
- LLM confidence score는 수학적 타당성과 calibration의 증명이 아니다.
- single transaction만 분석한다.
- 주소 통제·beneficiary·victim·loss bearer를 개별적으로 귀속하지 않는다.
- actual P&L·manipulation-attributable gain·victim counterfactual loss를 계산하지 않는다.
- 전용 hard-negative 평가가 부족하다.

## 15. 우리 연구에서의 사용 방법

DeFiScope에서 재사용할 수 있는 것:

- user-invocation 단위의 시간 순서가 있는 Transfer Graph
- raw transfer와 semantic operation 계층의 분리
- `Swap/Deposit/Withdraw/Borrow/Stake/Claim`을 대상으로 한 operation recovery 규칙과 평가 방식
- price-direction inference와 semantic pattern을 분리하는 파이프라인
- source가 없을 때의 fallback과 실패 보고 구조
- semantic recovery와 end-to-end detection을 분리한 평가

그대로 가져오면 안 되는 것:

- price direction을 distortion value로 간주
- pattern의 시간적 인접성을 consumption data-flow로 간주
- 실행 전 state가 없는데도 LLM의 단일 방향 출력을 증명으로 간주
- closed-source 2-token contract를 자동으로 CPMM으로 간주
- initiator를 공격자·최종 수혜자로 강제
- profit을 공격의 충분한 증거로 사용

우리 causal evidence representation은 최소한 다음을 분리해야 한다.

```text
swap execution rate
local pool price
custom valuation output
protocol-consumed value
settlement result
actual asset/debt change
counterfactual gain/loss
```

## 16. 최종 판정

DeFiScope는 **token transfer → semantic operation** 복원과 **balance/supply delta + price code → price direction** 추론을 결합해, 커스텀 가격 모델을 포함한 여러 PMA를 높은 recall로 검출하는 방법을 제공한다.

그러나 왜곡을 다음처럼 완전히 복원하지는 않는다.

```text
정상 reference
→ 조작된 정확한 value
→ value consumption
→ settlement
→ 반사실 추가이익·피해자 손실
```

따라서 이 논문은 **PMA 후보 탐지와 semantic lifting의 핵심 비교 대상**이지만, 우리가 목표로 하는 정확한 causal witness·role attribution·counterfactual P&L을 대체하지는 못한다.
