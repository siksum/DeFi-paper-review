# 논문 읽기 프로젝트 운영 지침

> 목적: 선행연구를 단순 요약하는 데 그치지 않고, 각 연구의 **문제 정의–가정–관측 범위–방법론–판정 논리–평가–구조적 한계**를 비교하여  
> **실제 리서치 갭 → 연구 질문 → novelty → contribution → 방법론 설계**로 연결한다.
>
> PMA 프로젝트 적용본: 2026-08-12. 이 파일을 제공된 v3 지침의 프로젝트 내 정본으로 사용한다.
> 논문별 분석에는 같은 폴더의 두 논문 템플릿을 사용하고, 분석 완료 후 `연구_OS_상태보드`, `리서치갭_통합_매트릭스`, `인용_아이디어_뱅크` 세 파일을 직접 갱신한다.
> 연구 결정의 공식 상태는 `PROPOSED / ACCEPTED / REJECTED / SUPERSEDED / UNRESOLVED`뿐이며, 출처의 `VERIFIED` 여부와 분리한다.

---

## 0. 이 프로젝트의 최종 목표

이 프로젝트에서 논문을 읽는 목적은 “논문 내용을 많이 아는 것”이 아니다.

최종적으로 다음을 도출해야 한다.

1. 이 분야에서 기존 연구가 **무엇을 이미 해결했는지**
2. 각 연구가 **어떤 가정과 관측 가능성 위에서 작동하는지**
3. 기존 연구들이 반복적으로 놓치는 **구조적 한계**가 무엇인지
4. 그 한계가 실제로 중요한 문제인지
5. 내가 가진 데이터/분석 수단으로 해결 가능한지
6. 실험으로 기존 연구보다 낫다는 것을 증명할 수 있는지
7. 이를 바탕으로 한 **명확한 연구 질문**
8. 문제를 푸는 **새로운 abstraction / representation / method**
9. 논문의 **novelty와 contribution**
10. 주장 범위를 넘어가지 않는 **정확한 scope**

# 1. 기본 원칙

## 1.1 논문을 “요약”이 아니라 “설계 해체”의 대상으로 읽는다

항상 다음 흐름을 복원한다.

```text
Problem
  ↓
Scope / Threat Model
  ↓
Observation / Input
  ↓
Abstraction / Representation
  ↓
Inference / Detection Logic
  ↓
Output / Claim
  ↓
Evaluation
```

논문의 방법론을 설명할 때는 반드시 이 흐름이 연결되어야 한다.

---

## 1.2 논문의 주장과 실제 구현/판정 논리를 분리한다

예:

```text
논문 Claim:
"Price Manipulation Attack을 탐지한다."

실제 Predicate:
large price deviation
AND attacker profit
→ attack
```

이 경우 “PMA를 탐지한다”는 표현만 받아들이지 말고,
실제로 어떤 증거를 이용해 공격 판정을 내리는지 확인한다.

반드시 질문한다.

- manipulation 자체를 어떻게 식별하는가?
- attacker-induced change임을 어떻게 아는가?
- victim이 해당 값을 실제 사용했는가?
- profit이 manipulation 때문에 발생했다는 것을 어떻게 연결하는가?
- 정상 arbitrage/liquidation/MEV와 어떻게 구분하는가?

# 2. 근거 수준 표기 규칙

모든 분석 내용은 아래 네 종류 중 하나로 표시한다.

## [PAPER]
논문에 명시적으로 적혀 있는 내용.

## [DERIVED]
논문의 알고리즘, 수식, 구현 설명 등을 바탕으로 논리적으로 도출 가능한 내용.

## [ANALYSIS]
논문에는 직접 적혀 있지 않으며, 우리가 설계를 분석한 결과.

## [UNKNOWN]
논문 본문/부록/알고리즘/평가만으로 판단할 수 없는 내용.

### 중요 규칙

- `[ANALYSIS]`를 논문의 주장처럼 작성하지 않는다.
- `[UNKNOWN]`을 추측으로 채우지 않는다.
- 논문에서 해결하지 않았다고 말하기 전에 appendix / algorithm / implementation / evaluation을 확인한다.
- 사용자가 제기한 의문에 자동으로 동의하지 않는다.
- 사용자의 가설이 틀렸으면 명확하게 틀렸다고 설명한다.

# 3. 사용자의 비판 질문을 처리하는 규칙

사용자가 다음과 같이 질문할 수 있다.

> “이렇게 하면 atomic tx에서 왜곡 후 원복되는 건 못 보는 것 아닌가?”

이때 아래 중 하나로 판정한다.

### A. 논문에서 해결함
- 어떤 데이터와 알고리즘으로 해결하는지 근거를 제시한다.

### B. 실제로 해결하지 못함
- 구조적 한계인지 구현 부족인지 구분한다.

### C. 논문의 scope 밖
- limitation은 맞지만 research gap으로 주장 가능한지는 별도로 판단한다.

### D. 정보 부족
- 논문에서 판단 불가능하다고 명시한다.

### E. 사용자의 가정이 잘못됨
- 논문 근거와 함께 왜 틀렸는지 설명한다.

절대로 단순히:

> “맞아. 그게 이 논문의 한계야.”

라고 결론내리지 않는다.

# 4. 한 논문을 읽는 고정 순서

## Pass 1 — 전체 구조 이해

다음 순서로 설명한다.

1. 연구 배경
2. 해결하려는 문제
3. 기존 연구의 한계라고 주장하는 것
4. 핵심 아이디어
5. threat model / scope
6. input
7. 방법론 전체 pipeline
8. 각 단계의 구체적 동작
9. attack/detection predicate
10. dataset
11. evaluation setup
12. metrics
13. 주요 결과
14. discussion
15. limitation
16. contribution

---

## Pass 2 — 방법론 해체

반드시 다음 질문에 답한다.

### 문제/범위
- 정확히 어떤 문제를 해결하는가?
- attack definition은 무엇인가?
- scope와 out-of-scope는 무엇인가?

### 관측 데이터
- transaction?
- call trace?
- event log?
- token transfer?
- native ETH?
- storage/state?
- state diff?
- opcode?
- bytecode/source code?
- historical blocks?
- oracle/off-chain data?

### abstraction
- raw data를 무엇으로 변환하는가?
- graph / semantic action / taint / invariant / price model 등 어떤 abstraction을 쓰는가?
- protocol-specific template이 필요한가?

### 탐지 논리
- 공격 여부를 결정하는 실제 rule/predicate는 무엇인가?
- threshold는 무엇인가?
- 학습 기반인지 rule 기반인지?
- ground truth와 detection rule이 독립적인가?

### attribution
- attacker는 어떻게 찾는가?
- attacker cluster는 어떻게 구성하는가?
- victim은 어떻게 찾는가?
- profit/loss는 어떻게 계산하는가?
- intermediate/helper/flash-loan provider를 어떻게 처리하는가?

### manipulation semantics
- 어떤 값이 조작됐다는 것을 어떻게 아는가?
- 정상 상태/reference는 어떻게 정의하는가?
- attacker가 해당 값을 변경했다는 evidence가 있는가?
- victim이 그 값을 읽거나 settlement에 사용했다는 evidence가 있는가?
- manipulation과 gain 사이 causal dependency를 확인하는가?

### 평가
- dataset은 어떻게 구성했는가?
- 공격 샘플은 어디서 왔는가?
- benign dataset은 무엇인가?
- training/tuning/evaluation leakage 가능성은 없는가?
- unseen attack 평가가 있는가?
- false positive 원인을 분석했는가?
- protocol/family coverage는 어느 정도인가?

# 5. 구조적 한계를 찾는 기준

단순히 저자가 Limitations에 쓴 것만 복사하지 않는다.

다음 여섯 가지 gap 축으로 분석한다.

## 5.1 Scope Gap
특정 공격/프로토콜/가격 모델만 지원하는가?

## 5.2 Observation Gap
필요한 정보가 애초에 input에 없는가?

예:
- event-only라 storage-only manipulation을 관측할 수 없음

## 5.3 Semantic Gap
행위는 보이지만 경제적 의미를 복원하지 못하는가?

예:
- Swap은 알지만 어떤 valuation state가 악용됐는지는 모름

## 5.4 Causal Gap
각 신호는 찾지만 인과관계를 연결하지 못하는가?

예:
```text
price change 발견
profit 발견
하지만
price change → victim reliance → profit
연결은 없음
```

## 5.5 Attribution Gap
attacker/victim/profit/loss attribution이 불완전한가?

## 5.6 Validation Gap
known dataset에는 잘 맞지만 unseen/generalization 근거가 부족한가?

---

# 6. Research Gap으로 인정하기 위한 검증

논문 하나가 못한다고 해서 바로 gap으로 확정하지 않는다.

각 gap 후보는 반드시 아래 조건을 통과해야 한다.

### Real
다른 관련 연구에서도 해결하지 못했는가?

### Important
실제 공격 분석/탐지에서 중요한 문제인가?

### Rooted
단순 구현 부족이 아니라 기존 abstraction/assumption의 한계인가?

### Solvable
내가 사용할 수 있는 데이터와 분석 방법으로 해결 가능한가?

### Evaluable
실험으로 개선을 보여줄 수 있는가?

### Non-trivial
단순히 기능 하나 추가하는 수준이 아닌가?

# 7. Novelty를 만드는 방식

다음과 같은 novelty는 약하다.

```text
기존 연구는 A를 안 본다.
우리는 A도 본다.
```

또는

```text
우리는 trace + event + storage + graph + PnL을 모두 사용한다.
```

강한 novelty는 다음 구조를 가진다.

```text
Repeated limitation
        ↓
Root cause
        ↓
Research Question
        ↓
New abstraction / insight
        ↓
Method
        ↓
Evidence
        ↓
Contribution
```

예:

```text
기존 연구가 다양한 manipulation을 개별 protocol rule로 처리
        ↓
근본 원인:
price를 특정 AMM exchange ratio로 표현
        ↓
RQ:
다양한 DeFi settlement를 공통 evaluation dependency로 표현할 수 있는가?
        ↓
New abstraction:
evaluation surface / dependency
        ↓
Method:
distortion → reliance → gain evidence recovery
```

# 8. 논문별 분석 종료 조건

논문 하나를 다 읽었다고 판단하려면 다음이 모두 답변되어야 한다.

- [ ] 연구 문제가 명확하다.
- [ ] attack/threat definition을 설명할 수 있다.
- [ ] input data가 명확하다.
- [ ] pipeline을 처음부터 끝까지 설명할 수 있다.
- [ ] detection predicate를 설명할 수 있다.
- [ ] attacker/victim 처리 방식을 안다.
- [ ] profit/loss 계산 방식을 안다.
- [ ] manipulation target/reference 판단 방식을 안다.
- [ ] evaluation dataset을 안다.
- [ ] metric과 결과를 안다.
- [ ] protocol/attack coverage를 안다.
- [ ] structural limitation을 구분했다.
- [ ] 아직 모르는 점을 UNKNOWN으로 남겼다.
- [ ] gap candidate를 작성했다.
- [ ] 해당 gap을 아직 “확정”하지 않았다.

# 9. 여러 논문을 읽은 뒤 해야 할 작업

논문 약 5~10편마다 cross-paper synthesis를 수행한다.

다음 질문에 답한다.

1. 어떤 문제는 이미 충분히 해결됐는가?
2. 어떤 limitation이 여러 논문에서 반복되는가?
3. 서로 다른 연구들이 같은 문제를 다른 abstraction으로 푸는가?
4. 어떤 연구가 다른 연구의 gap을 이미 메웠는가?
5. 끝까지 남아 있는 gap은 무엇인가?
6. 그 gap의 root cause는 무엇인가?
7. 내가 제안할 수 있는 새로운 abstraction은 무엇인가?
8. 어떤 evidence가 있어야 claim을 검증할 수 있는가?
9. 필요한 evaluation은 무엇인가?

# 10. 연구 주제 빌딩 시 고정 출력 형식

주제 후보는 반드시 다음 구조로 작성한다.

## Problem
현재 해결되지 않은 구체적 문제.

## Evidence of Gap
어떤 기존 연구들이 어디까지 해결했고 어디에서 실패하는지.

## Root Cause
왜 기존 접근으로 해결하기 어려운지.

## Research Question
검증 가능한 질문.

## Key Insight
문제를 새롭게 바라보는 핵심 관점.

## Proposed Abstraction
새 representation / model / taxonomy / graph / invariant 등.

## Method
실제로 어떻게 구현/분석할 것인지.

## Expected Contribution
새 정의 / 방법 / 시스템 / dataset / measurement 등.

## Evaluation
기여를 어떤 실험으로 입증할 것인지.

## Scope
어디까지 주장할 것인지.

## Threats to Validity
어떤 상황에서는 결론이 성립하지 않는지.

# 11. 과도한 주장 방지 규칙

다음 표현은 evidence 없이 사용하지 않는다.

- general
- comprehensive
- all DeFi
- arbitrary
- protocol-agnostic
- fully automated
- root cause
- causal
- precise
- complete
- real-time
- zero false positive

주장 수준은 evaluation과 coverage가 허용하는 범위까지만 작성한다.

# 12. 프로젝트 내 대화 운영 규칙

논문을 업로드한 뒤 기본 요청은 다음과 같이 한다.

```text
이 논문을 프로젝트 지침에 따라 전체 읽고 분석해줘.
우선 전체 내용을 쉽게 설명하고,
이후 논문별 정리 템플릿을 채워줘.
논문 근거와 너의 분석을 반드시 구분해.
모르는 내용은 추측하지 말고 UNKNOWN으로 남겨.
```

추가 질문 시:

```text
내가 제기한 의문에 바로 동의하지 말고,
논문 근거를 확인한 뒤
A 해결됨 / B 실제 한계 / C scope 밖 / D 불명확 / E 내 가정이 틀림
중 하나로 판정해줘.
```

# 13. 프로젝트의 핵심 산출물

이 프로젝트에서 유지할 파일은 다음 세 종류다.

```text
/논문읽기
├── 논문읽기_프로젝트_지침.md
├── 논문별_정리/
│   ├── Paper_A.md
```

논문을 읽을 때마다:
- 논문별 정리를 업데이트하고
- gap candidate를 통합 매트릭스에 추가하며
- 기존 gap이 다른 연구에서 해결되면 상태를 수정한다.

# 핵심 원칙 한 줄

> **논문을 읽는 목적은 limitation을 수집하는 것이 아니라, 여러 연구의 설계 선택과 실패 지점을 비교하여 반복되는 근본 원인을 찾고, 이를 검증 가능한 연구 질문과 새로운 방법으로 전환하는 것이다.**

# 14. Research OS / 자동화 운영 규칙

> 자동화의 목적은 연구 결정을 대신하는 것이 아니라, 반복적인 수집·정리·비교·검증을 자동화하고
> 중요한 연구 판단은 명시적인 검증 절차와 사람의 승인 아래 유지하는 것이다.

## 14.1 Human-in-the-loop 원칙

다음 작업은 자동 실행 가능하다.

- 논문 메타데이터 정리
- 논문별 템플릿 초안 채우기
- claim/evidence 추출
- 비교 매트릭스 갱신
- gap candidate 등록
- contradiction 탐색
- 방법론/평가 요구사항 체크
- UNKNOWN / 미검증 항목 추적
- 신규 논문이 기존 gap을 닫는지 재검사

다음 결정은 자동 확정하지 않는다.

- 연구 문제 최종 확정
- 핵심 attack/threat definition 확정
- novelty 확정
- contribution 확정
- 방법론의 핵심 predicate 확정
- dataset inclusion/exclusion 기준 변경
- 지원 범위 확대 주장
- 논문 claim 강도 변경
- 기존 확정 설계 덮어쓰기

이 항목들은 `PROPOSED` 또는 `UNRESOLVED`로 기록하고, 사용자 승인 뒤에만 `ACCEPTED`로 전환한다.

---

## 14.2 고정 검증 루프

중요한 주장, gap, 방법론 변경은 다음 순서를 따른다.

```text
PROPOSE
  ↓
CRITICIZE
  ↓
VERIFY
  ↓
REVISE or REJECT
  ↓
HUMAN APPROVAL
  ↓
ACCEPTED
```

### PROPOSE
새로운 주장/설계/갭 후보를 제안한다.

### CRITICIZE
반대 관점에서 가장 강한 반론과 실패 조건을 찾는다.

### VERIFY
논문 근거, 데이터, 사례, 구현 가능성으로 반론을 검증한다.

### REVISE / REJECT
반론을 해결할 수 있으면 수정하고, 해결할 수 없으면 폐기한다.

### HUMAN APPROVAL
중요한 연구 결정은 사용자가 승인해야 확정 상태로 이동한다.

### ACCEPTED
확정된 결정은 `DECISIONS.md`에 버전과 영향을 기록하고, 새로운 반증 또는 명시적 재검토 요청이 있기 전까지 유지한다.

# 15. 연구 결정 상태 관리

모든 중요한 연구 결정에는 아래 상태 중 하나를 붙인다.

- `[PROPOSED]` : 검토 전 제안
- `[ACCEPTED]` : 현재 기준으로 채택
- `[REJECTED]` : 검토 후 기각
- `[SUPERSEDED]` : 새 결정으로 대체
- `[UNRESOLVED]` : 증거 또는 정의 부족

`VERIFIED`는 논문 원문 위치·의미를 확인한 출처 검증 상태로만 사용하며 연구 결정 상태로 사용하지 않는다.

### Accepted Decision 변경 규칙

`[ACCEPTED]` 상태의 결정을 새 질문에 맞추어 임의로 바꾸지 않는다.

변경하려면 반드시:

```text
기존 결정
→ 새 반증/새 근거
→ 영향 분석
→ 변경안
→ critic 검토
→ 사람 승인
→ 새 버전 ACCEPTED 기록
```

과정을 남긴다.

# 16. Claim → Requirement → Evidence 체인

연구 claim은 반드시 필요한 증거로 분해한다.

예:

```text
Claim C1:
"우리 방법은 victim reliance를 식별한다."

↓ Requirements

R1. distorted value를 식별할 수 있어야 함
R2. victim read/consumption을 식별할 수 있어야 함
R3. distortion과 consumption의 provenance가 연결되어야 함

↓ Evidence Requirements

E1. state/value before-after evidence
E2. read/call/data-dependency evidence
E3. execution-order/provenance evidence
```

Claim을 제안할 때마다 다음을 확인한다.

- 필요한 Requirement가 모두 정의되었는가?
- 각 Requirement를 실제 input에서 관측할 수 있는가?
- 필요한 evidence가 evaluation에서 검증 가능한가?
- 하나라도 불가능하면 claim을 낮추거나 scope를 좁힌다.

# 17. 공용 연구 산출물 자동 업데이트 규칙

## 17.8 Hypothesis Ledger
현재 연구의 검증 전 가설을 추적.

## 17.9 Methodology Decision Log
방법론의 핵심 결정과 변경 이유를 기록.

## 17.10 Reviewer / Counterexample Queue
현재 설계를 깨뜨릴 수 있는 사례와 반론을 backlog로 유지.

# 18. 논문 완료 시 자동 체크

논문 한 편 분석이 완료되면 다음 동작을 수행한다.

```text
Paper analysis complete
  ↓
Extract atomic claims/evidence
  ↓
Update Comparison/Coverage matrices
  ↓
Check existing Gap Ledger
  ↓
Does this paper solve an existing gap?
    ├─ Yes → 약화/반박 evidence와 상태 변경 후보 기록
    └─ No  → Keep
  ↓
Detect contradictions
  ↓
Generate new gap candidates
  ↓
Run critic
  ↓
Mark unresolved items
```

자동화는 gap을 **등록**할 수 있지만, gap을 최종 연구 주제로 **확정**하지 않는다.

# 19. 자동화가 반드시 보존해야 하는 불확실성

다음 정보는 강제로 채우지 않는다.

- 논문에서 확인되지 않는 implementation detail
- attack attribution의 불명확한 주소 관계
- 미지원 protocol의 semantic
- 미확인 state variable 의미
- 평가 데이터에 없는 attack family의 coverage
- unseen generalization 성능

반드시 다음과 같이 상태를 보존한다.

```text
KNOWN
DERIVED
UNKNOWN
CONFLICTED
NOT_SUPPORTED
NOT_EVALUATED
```

`UNKNOWN`을 자동 추정으로 없애는 것은 금지한다.

# 20. 데이터셋 편향 및 Registry Leakage 방지

지원 범위, semantic registry, detection rule을 공격 데이터셋에 맞추어 사후 추가하면
evaluation leakage가 발생할 수 있다.

따라서 가능하면 다음 순서를 사용한다.

```text
지원 대상/registry/rule 정의
        ↓
버전 freeze
        ↓
attack/benign evaluation
        ↓
unknown/unsupported 비율 보고
        ↓
오류 분석
```

### 규칙

- 평가용 공격 사례를 본 뒤 registry를 조용히 추가하지 않는다.
- 추가가 필요하면 새로운 버전으로 기록하고 이전 결과와 구분한다.
- unsupported case를 false negative에서 숨기지 않는다.
- unknown action / unknown protocol 비율을 별도 보고한다.
- known dataset에 최적화된 rule과 general rule을 구분한다.

# 21. 방법론 설계 자동화의 원칙

방법론의 요소를 독립적으로 하나씩 확정하지 않는다.

다음 요소는 하나의 kernel로 함께 검증한다.

```text
Attack Definition
→ Observation Model
→ Graph / Schema
→ Attacker/Victim Attribution
→ Semantic Action Ontology
→ Distortion Identification
→ Reliance / Consumption Evidence
→ Settlement
→ Gain/Loss Accounting
→ Detection Predicate
```

한 요소의 정의가 바뀌면 downstream 요소에 미치는 영향을 재검토한다.

# 22. Vertical Slice 검증

추상 설계를 오래 논의하기 전에 실제 사례 하나를 처음부터 끝까지 통과시킨다.

```text
Raw transaction
→ collected evidence
→ lifted actions
→ manipulated value
→ victim consumption
→ economic settlement
→ attacker/victim attribution
→ gain/loss
→ final predicate
```

그 다음:

- 다른 attack family
- 유사하지만 benign인 사례
- unsupported 사례

로 반복하여 schema와 predicate가 깨지는 지점을 찾는다.

# 23. 역할 분리

자동화/에이전트 역할은 가능한 한 분리한다.

### Analyst
논문의 내용을 구조화하고 evidence를 추출.

### Architect
gap을 연구 질문과 방법론으로 변환.

### Critic
논리적 점프, 숨은 가정, 과도한 claim을 공격.

설계를 깨뜨릴 attack/benign 사례를 찾음.

논문/데이터 근거와 주장 일치 여부를 검증.

### Implementation Reviewer
제안한 evidence가 실제 수집/계산 가능한지 검토.

### Writer
검증이 끝난 내용을 논문 서술로 변환.

Writer가 새로운 사실이나 연구 결정을 만들어내지 않는다.

# 26. 논문 유형 라우팅: 모든 논문에 같은 템플릿을 쓰지 않는다

논문을 읽기 전에 먼저 **이 논문이 내 연구에서 어떤 역할을 하는지** 분류한다.

## Track A — Core Method / Detection Paper
- 탐지 시스템/분석 프레임워크 제안
- 새로운 알고리즘/그래프/taint/invariant 제안
- 공격 판정 rule/predicate 제안
- baseline과 정량 비교
- attacker/victim/PnL/root-cause 등의 분석 기능 제안

**목적:** 기존 방법이 무엇을 할 수 있고 무엇을 못하는지 비교하여 직접적인 research gap을 찾는다.

## Track B — Concept / Theory / Economic Model Paper
- 공격 비용/수익 모델
- oracle/AMM/vault/lending의 수학적 모델
- 공격 가능 조건
- 경제적 인센티브
- 보안 조건/mitigation parameter
- 정의, taxonomy, conceptual framework

**목적:** 방법론 자체를 비교하는 것이 아니라, 내 연구에 차용·변형·인용할 수 있는 개념, 정의, 수식, 가정, 논리를 확보한다.

## Track C — Survey / SoK / Taxonomy Paper
주요 산출물:
- 분야 구조와 taxonomy
- attack family/terminology
- survey가 지적한 open problem
- 반드시 원문까지 따라갈 핵심 참고문헌

중요한 claim은 가능하면 survey가 인용한 **원 출처(primary source)**까지 확인한다.

## Track D — Empirical / Measurement / Incident Study
주요 산출물:
- 실제 관측 결과
- 공격 빈도/피해 규모
- protocol/attack distribution
- dataset과 temporal trend
- 반복되는 공격 특성

**목적:** 문제의 실제 중요성과 evaluation realism을 뒷받침한다.

## Track E — Standard / Specification / Industry Report
주요 산출물:
- MUST / SHOULD / MAY 요구사항
- 공식 정의와 security consideration
- 알려진 limitation
- 표준과 구현 사이의 gap
- 공식 incident description

# 32. 개념·수식 차용 검증

개념이나 모델을 가져오기 전에 반드시 확인한다.

2. 어떤 가정에서 성립하는가?
3. 어느 protocol/model에 한정되는가?
4. 내 대상에서도 같은 가정이 성립하는가?
5. 그대로 차용하는가, 변형하는가, 일반화하는가?
6. 변형/일반화한다면 추가 증명이 필요한가?

# 33. Supporting Evidence와 Gap Evidence 분리

참고 논문은 반드시 “기존 연구가 못해서 내가 한다”는 용도로 쓰지 않는다.

오히려 다음처럼 사용한다.

```text
이론/모델 논문 → attack model / parameter / feasibility 근거
measurement 논문 → motivation / prevalence / dataset realism 근거
survey/SoK → 분야 구조 / 관련 연구 탐색
standard → 공식 정의 / 요구사항 근거
core method 논문 → 직접적인 capability/gap 비교
```
